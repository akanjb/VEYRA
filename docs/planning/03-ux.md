# Phase 3 — UI/UX Plan

**Benchmark.** AgentTelemetry has the strongest analytical presentation of the references. OpenUsage is the reference for compact quota monitoring. Veyra's design is original. We take *principles* from them (restraint, colour reserved for data, a headline number with its change, a table behind every chart), not their layouts, CSS or palette. Veyra goes further in three areas:

1. accuracy is visible everywhere;
2. drill-down works across every module;
3. the information hierarchy is grouped by question, not by data source.

## 1. Design principles

1. **Answer first.** Every page opens with the one number that answers its question, the change against a comparison period, and its accuracy.
2. **Calm chrome, expressive data.** Interface chrome is neutral and monochrome. Colour is reserved for data series and meaningful status.
3. **Stable identity colours.** A provider always has the same hue. Models are tints within their provider's hue family, so a model is recognisable as Anthropic or OpenAI by colour alone.
4. **Trust is visible.** Every number can show its accuracy composition, definition and assumptions within one hover or click.
5. **Progressive depth.** Summary → breakdown → table → session → event timeline. Nothing important is more than two clicks away.
6. **Keyboard and screen-reader complete.** Charts are never the only way to read data.

## 2. Information architecture

### 2.1 Sitemap and sidebar

The sidebar has grouped sections; the order follows the user's questions.

```
VEYRA
  Overview                      "How am I using AI overall?"
ANALYZE
  Usage                         "What is consumed, and where?"
  Cost                          "What does it cost — estimated, actual, subscription?"
  Cache                         "Is caching working, and what does it save?"
  Models & Providers            "Which models do I use and how do they compare?"
  Tools & Agents                "What work do the agents perform?"
  Activity                      "When do I work with AI?"
EXPLORE
  Projects  →  Project detail  →  Session detail
  Sessions  →  Session detail  (event timeline drawer/page)
PLAN
  Quotas & Limits               "How close am I to my limits?"
  Optimization                  "What could I do better?"
SYSTEM
  Sources & Health              connectors, coverage, freshness, errors, consent
  Storage                       footprint, retention, backups
  Organization                  (hidden until enabled) pairing, sharing preview, policy
  Settings                      general, time zone, privacy, pricing overrides, billing entries, budgets, appearance, updates, data
```

**Why these changes from the brief's 15 items.**
- *Budgets* and *billing entries* live inside **Cost** for viewing and **Settings** for editing. They are not a separate page.
- *Devices* becomes a filter dimension and a section on **Overview** and **Usage**. The org-specific features go in **Organization**.
- *Diagnostics* merges into **Sources & Health**, because users diagnose by source.

### 2.2 Global frame

```
┌──────────────┬───────────────────────────────────────────────────────────────────────────┐
│  ◆ Veyra     │  Overview                                   ⌘K   ⟳ 12s ago  ● 4 sources  │
│              │  ────────────────────────────────────────────────────────────────────────  │
│  Overview    │  Showing [Tokens ▾] for [All apps ▾] · [Last 30 days ▾] ‹ ›  vs [prev ▾]  │
│  ANALYZE     │  [Project: veyra ×] [Model: claude-sonnet-5-5 ×]   Exact 96% · Est 4% ⓘ   │
│  Usage       │  ────────────────────────────────────────────────────────────────────────  │
│  Cost        │                                                                           │
│  Cache       │   (page content)                                                          │
│  …           │                                                                           │
│  ──────────  │                                                                           │
│  ⚙ Settings  │                                                                           │
│  ◐ Theme     │                                                                           │
└──────────────┴───────────────────────────────────────────────────────────────────────────┘
```

**Header.** It shows the page title and a status cluster:
- last-updated time, live while ingestion runs;
- source-health dot plus a count, which links to Sources;
- the command palette (`Ctrl/⌘ K`).

**Query bar.** A readable, editable sentence: *measure · scope · period · comparison*. Each token is a menu; the period has ‹ › stepping.
- Measures: Tokens, Cost (API-equivalent), Requests, Sessions, Active time.
- Comparison: previous period, same period last month, same period last year, or none.
- Advanced filters open one **Filters panel**: provider, model, app, interface, gateway, project, device, accuracy ("Exact only").
- Active filters show as removable chips.
- All of this state lives in the URL (single source), so back/forward, deep links and the future localhost/Hub views work identically.

**Coverage meter.** Shows the accuracy composition of the current scope, plus pricing coverage on cost views. Clicking it opens an explanation and links to the sources responsible.

**Sidebar.** Collapses to an icon rail below 1200 px wide, or manually with `[`. On localhost or Hub mobile widths it becomes a drawer.

## 3. Page anatomy (consistent across modules)

```
Page header        title · one-line purpose · page actions (Export ▾, Table/Chart toggle)
KPI strip          1 hero metric (large, delta chip, sparkline, accuracy badge) + 3–5 supporting tiles
Primary chart      full width, the page's main question over time
Secondary grid     2 columns (1 below 1100 px): breakdowns/compositions
Detail table       sortable, searchable, virtualised; row click → drill-down
```

**Card anatomy.** Every card has:
- a title;
- an ⓘ icon showing the definition from the metric registry;
- an accuracy badge;
- a chart/table toggle (⊞);
- an overflow menu (export card data, copy, view sessions).

All cards follow one 8 px spatial grid and three height classes (S/M/L), so rows align.

## 4. Modules: content and chart choices

The chart choice follows the question each card answers. For each module, the table lists its cards in order.

### Overview
| Card | Visualisation | Notes |
|---|---|---|
| Hero: total tokens (or the selected measure) | Big number + delta + sparkline | Comparison from the query bar |
| Supporting tiles | API-equiv. cost · Requests · Sessions · Active time · Cache hit ratio | Each with delta and accuracy |
| Daily trend by application | Stacked bars (≤ 14 bars) / stacked area (> 30 days), toggle | Click a day → filters the period to that day |
| Provider and model mix | Horizontal ranking bars with share %, top 8 + Other | A donut is offered only as an option; ranking bars read better |
| Project distribution | Treemap (top 30) with table twin | Click → Project detail |
| Activity calendar (12 months) | Calendar heatmap | Click a day → sets the period |
| Hour × weekday | Heatmap in the user's time zone | |
| Highlights | 3–5 deterministic insight chips ("Busiest day…", "Top project…", "Cache saved…") | From the analytics engine, not free text |

### Usage
- Token composition over time: stacked area of input uncached, cache read, cache write and output, with a reasoning overlay line.
- Breakdowns by model, provider, app, interface, project and device. Each is a ranking bar plus a table, chosen through a tab group.
- Average tokens per request and per session: line chart with a P50/P90 band.
- Distribution of request sizes: histogram on a log-x axis.
- Concentration: a Pareto chart (cumulative-share line over sorted bars).

### Cost
- **Three cost columns are never summed:**
  - **API-equivalent estimate**, with pricing coverage;
  - **Actual charges** (when connected or entered);
  - **Subscription spend** (manual or reported).
- **Value framing.** "Subscription $X · usage would cost $Y at API rates" is shown as a *comparison*, never as a total.
- Daily cost: bars, plus a cumulative line on a secondary axis.
- Cumulative cost against the previous period: two lines.
- Month-to-date, run rate and forecast: a line with a projected dashed segment and budget threshold lines.
- Cost by model, provider, app, project and session: ranking bars with a table.
- Cost composition by token type: 100% stacked bar.
- Effective $/1M output tokens by model: dot plot, sorted.
- Period change: a **waterfall chart** of the contribution to change by model or project.
- Assumptions panel (side sheet): the rules, rates, tiers and modifiers used; stale and unpriced items.
- Budgets: progress meters, with threshold states using semantic colours.

### Cache
- Hero: net cache benefit. Supporting tiles: gross saving, write overhead, hit ratio, reuse ratio.
- Cache read and write over time: mirrored area (reads above the axis, writes below).
- Hit ratio by model and by project: ranking bars.
- 5m vs 1h writes and their reuse: grouped bars.
- Inefficiency list: sessions with high writes and low reuse. Rows link to Optimization findings.

### Models & Providers
- Provider share over time: 100% stacked area.
- Model leaderboard table:
  - requests, tokens and cost;
  - $/1M output tokens;
  - cache hit ratio;
  - price coverage and context window (verified flag);
  - lifecycle state (current, deprecated, retired).
- Provider × application matrix: heatmap table.
- Model × application matrix.
- Model timeline: Gantt-like swimlanes showing when each model was used.
- Comparison mode: pick 2–4 models to see side-by-side KPIs and a radar-free bar comparison. Radar charts are avoided because they distort comparisons.
- A tokenizer note: models on different tokenizer generations get a comparability warning.

### Tools & Agents
- Tool calls per request and per session: trend line.
- Calls by category (file, search, shell, web, MCP, subagent): stacked bars over time.
- Top tools and MCP servers: ranking, with an error-rate column.
- Main agent vs subagent consumption: split bar plus trend.
- Tool-heavy sessions against tokens: **scatter** (x = tool calls, y = tokens, colour = app), with outlier drill-down.
- Error and retry signals: only where the source records tool-result errors; labelled with their definitions.
- The page states plainly that higher token use is **not** treated as lower productivity.

### Activity
- Calendar heatmap (year); hour × weekday heatmap; daily active time vs wall time (paired bars).
- Peak hours and most active days (ranking).
- Session length distribution (histogram, active vs wall toggle).
- Long-running sessions list.
- Each card shows how active time is defined (idle threshold T).

### Projects → Project detail
- List: sortable table with sparklines (tokens, cost, sessions, active time, top model, last active), search, and merge/rename actions.
- Detail page:
  - a KPI strip and daily trend;
  - model, provider and application mix;
  - the most expensive sessions;
  - cache efficiency;
  - tool categories.
- Breadcrumbs: Projects › veyra › Session …

### Sessions → Session detail
- Explorer: virtualised table with column chooser, filters and saved views.
- Detail view (a page, also openable as a drawer):
  - header: app, interface, model(s), project, device, start/end, active vs wall time;
  - token and cost breakdown with the assumptions;
  - **event timeline** (a time axis with request markers sized by tokens and coloured by model, where model transitions show as colour changes);
  - tool-call lane;
  - subagent lanes nested under the parent.
- No prompt or response text is shown. Titles appear only if enabled.

### Quotas & Limits
- One card per provider account and window (e.g. Claude 5-hour, 7-day, model-specific). Each card shows:
  - a utilisation meter;
  - the reset countdown;
  - **"observed 3 min ago via Claude Code statusline"**;
  - provenance;
  - burn rate and projected time to exhaustion (labelled projection).
- Historical utilisation: a line chart with a reset marker for each window.
- Subscription and API accounts are clearly separated.
- Unsupported providers are listed with *why* and what would enable them.

### Optimization
- Findings list, sorted by measurable impact. Each finding shows:
  - title;
  - confidence;
  - impact range;
  - an evidence chart or table;
  - the method;
  - "affected sessions" (with drill-down);
  - dismiss or snooze.
- Combined impact uses overlap-aware totals, with a note.
- Each rule's thresholds can be configured (in Settings).

### Sources & Health
- Connector cards showing:
  - detected or not, enabled, consent state;
  - root path;
  - last success and freshness;
  - events ingested;
  - error count with an error log;
  - parser version and tested tool versions;
  - the **capability matrix** (metric → accuracy).
- Unsupported applications are listed with the reason ("Windsurf: no local usage data; Enterprise analytics API only").
- Actions: rescan, pause, re-ingest from scratch, open docs.

### Storage
- Database size and growth (area chart).
- Per-table sizes (bar).
- Events per month.
- Backups (list, restore with preview).
- Source directory sizes: size only, with a note that Veyra never deletes them.
- Retention policy editor, previewing the effect before applying it.

### Organization (when enabled)
- Pairing state and hub URL.
- **Sharing preview**: the exact payload of the next batch.
- Policy summary.
- Pause and leave controls.
- Audit of uploads.

### Settings
- General: start at login, run in background, time zone, week start, locale and number format.
- Privacy: session titles (off/truncated/full), project-hashing defaults.
- Pricing: overrides, custom models, stale threshold, catalogue update opt-in.
- Billing: subscriptions and manual charges.
- Budgets.
- Appearance: theme (light/dark/system) and density (comfortable/compact).
- Updates (opt-in).
- Data: export/import settings, delete Veyra data.

## 5. Design system

### 5.1 Tokens

There is one source: `styles/tokens.css` (Tailwind `@theme`). The chart theme reads the same CSS variables at runtime.

| Token group | Definition |
|---|---|
| Colour: chrome | Neutral ramp of 12 steps (cool gray), light and dark sets; surfaces `bg`, `surface`, `surface-raised`; borders hairline 1 px |
| Colour: accent | One accent (deep indigo-blue) for focus, selection and primary actions only |
| Colour: data | 10-slot categorical palette, colour-blind-safe, contrast-checked against both themes. A script in CI validates ΔE separation and contrast. The registry assigns provider slots; model tints are generated within the provider's hue |
| Colour: sequential | Single-hue ramp (7 steps) for calendars and heatmaps; a diverging ramp for deltas |
| Colour: semantic | success / warning / danger / info, used only for states (budget thresholds, errors, health). Not used for "more" or "less" |
| Colour: accuracy | Exact = solid; Provider-reported = solid with ring; Estimated = dotted outline + "≈"; Partial = half-filled; Unsupported = muted dash. **Shape and text carry the meaning, not colour alone** |
| Typography | Inter (bundled, OFL): 12/13/14/16/20/24/32/40 scale; `font-variant-numeric: tabular-nums` for all figures; JetBrains Mono (OFL) for ids and paths |
| Spacing | 4 px base; layout steps 8/12/16/24/32/48 |
| Radius | 6 (controls), 10 (cards), 14 (sheets) |
| Elevation | Borders first; one subtle shadow for overlays only |
| Motion | 120–200 ms ease-out on state changes; none on data load; respects `prefers-reduced-motion` |
| Density | Comfortable (default) and compact (−25% vertical padding, smaller table rows) |

**Number formatting** (`shared/format`, single source):
- Compact large numbers (12.4M).
- Full precision on hover.
- Currency with the user's locale. Estimated values are prefixed "≈".
- Percentages with one decimal below 10%.
- Durations as `3h 12m`.

### 5.2 Chart conventions

- Hairline gridlines; the y-axis starts at zero for bars; no 3D; no dual axes except the explicit cumulative overlays.
- Legends at the top left, interactive (click to isolate).
- Tooltips list values in the series' visual order, with units, share, accuracy marker and change.
- Ranked breakdowns cap at the top N (configurable) plus an exact "Other".
- Empty, low-data and "partial data" states are drawn inside the chart frame, never as a blank canvas.
- Every chart has a table twin with the same columns as its tooltip.

### 5.3 Components (owned, shadcn-based)

Button, IconButton, Menu, Popover, Tooltip, Dialog, Sheet, Tabs, SegmentedControl, Select/Combobox (searchable for hundreds of models and projects), DateRangePicker, Chip, Badge, AccuracyBadge, CoverageMeter, KpiTile, DeltaChip, Sparkline, Card, EmptyState, ErrorState, Skeleton, DataTable, CommandPalette, Toast, Breadcrumbs.

## 7. Key journeys

1. **First run (UC-01).**
   1. Welcome screen states the privacy promise in plain language.
   2. **Detected sources** list, with folders and fields read and not read; the user toggles each and continues.
   3. Import progress per source, with an ETA. The overview fills in progressively and is usable immediately.
   4. Optional quick setup: time zone, subscriptions, budget.
2. **Spike investigation (UC-03).**
   1. Overview hero shows +38%.
   2. Click the bar for the spike day; the period narrows to that day.
   3. The Sessions table is sorted by cost.
   4. Open a session to see its timeline: a model switch to a top tier, and heavy cache writes.
   5. An Optimization finding is linked.
3. **Monthly client report (UC-08).** Projects › client-x › Export ▾ › "Monthly cost report", with redaction toggles and a preview, then the native save dialog.
4. **Enable quota tracking (UC-06).** Quotas › Claude › "Enable via statusline". A guided snippet the user adds to their own Claude Code settings, with a copy button and a verification check. Veyra never edits Claude's settings itself.
5. **Org pairing (UC-11).** Organization › Join. Enter the hub URL and invite code, review the policy and sharing preview, then confirm.

## 8. States

- **Loading.** Skeletons match the final layout (no layout shift). Ingestion progress shows in the header, not as blocking spinners.
- **Empty.** Explains why ("No Gemini CLI sessions found in the selected period"), with next steps (change the period, enable a source, read the connector docs).
- **Partial data.** An inline banner on affected cards ("Cursor values are estimates; excluded from totals while 'Exact only' is on").
- **Error.** Card-level errors with retry. Page-level only when the backend is unavailable. Correlation id for support.
- **Stale.** Quota and price staleness is shown with a time and a muted style.

## 9. Accessibility

- Every control is reachable by keyboard and has a visible focus ring (accent, 2 px).
- Skip-to-content link. Landmarks and headings are structured.
- Shortcuts:
  - `/` focuses search;
  - `g o`, `g c` and similar jump to pages;
  - `[ ]` collapses the sidebar;
  - `, .` steps the period;
  - `Ctrl/⌘ K` opens the command palette;
  - `?` lists all shortcuts.
- Charts get `aria-label` summaries generated from the view model ("Tokens rose 38% to 12.4M…"), with the table twin as the accessible alternative.
- Contrast is checked for text, data marks against the background, and semantic states. Colour is never the only carrier of meaning.
- Automated axe checks run in Playwright on every page in both themes.

## 10. UX acceptance criteria

1. Every module page passes axe with no serious or critical issues in light and dark themes.
2. Changing any global filter updates every visible card consistently, and back/forward restores the previous state.
3. Every chart has a table twin with identical values (tested).
4. Accuracy badges and coverage are present on every aggregate metric.
5. Pages remain usable with 500 projects, 300 models and 1M sessions (virtualised lists, searchable selectors).
6. A first-time user can complete UC-02 without help in a moderated usability test (5 participants). This is the one manual check.
